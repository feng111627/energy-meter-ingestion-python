# 本地电表读数采集与用电量统计服务

基于 FastAPI + SQLite 的本地服务：接收模拟设备上报的**累计电表读数**，
按时间整理后计算相邻读数之间的用电增量，并支持按设备和时间窗口查询
用电量统计。重点处理真实场景中的计数器回绕、设备重启、重复上报、
时间倒序、离线空档、并发提交与服务重启等问题。

## 运行环境

- Python >= 3.14（项目按 3.14.4 开发），依赖管理用 [uv](https://docs.astral.sh/uv/)
- 安装：`uv sync`

## 快速开始

```bash
# 1) 运行单测（38 个用例，日志按业务分组打印覆盖情况）
uv run python -m pytest -v

# 2) 运行端到端模拟（多设备/回绕/异常/空档/并发/重启，无需网络）

# 3) 启动 HTTP 服务（默认持久化到 data/energy.db）

#   可用环境变量 METER_DB 指定数据库文件，默认 data/energy.db
#   API 文档：http://127.0.0.1:8000/docs
```

## 读数语义

- 每条上报是某台设备电能累计计数器在某一时刻的**快照**：
  `(device_id, timestamp, value)`，`value` 单位 kWh，物理上单调不减。
- **用电量 = 相邻两条读数之差**。读数 `(t1, v1)` 与 `(t2, v2)`（t1 < t2）
  之间的用电量记在区间 `(t1, t2]` 上，值为 `v2 - v1`。
- 每台设备的**第一条读数只是累计基线**，之前没有读数，其增量不定义，
  不计入任何用电量。
- 时间戳无时区时按 UTC 处理；带时区的统一换算为 UTC 存储，保证排序与
  查询结果稳定。

## 异常读数处理规则（可区分、可解释）

上报入口 `POST /api/readings` 返回三种状态；被拒绝的读数**不会入库**，
HTTP 状态码 422，响应体 `detail.reason` 给出机器可读原因、`detail.detail`
给出中文说明。

| 场景 | 判定 | 处理 | status / reason |
|---|---|---|---|
| 正常递增 | 新值 ≥ 上一条值 | 接受，增量 = 差值 | `accepted_new` |
| 重复上报 | 同设备同时间点，值也相同 | **幂等接受**，不产生增量、不重复计入 | `accepted_duplicate` |
| 同点冲突 | 同设备同时间点，但值不同 | 拒绝（同一时刻不可能有两个读数） | `rejected / conflict` |
| 时间倒序 | 时间戳严格早于该设备最新读数 | 拒绝（避免算出穿越式的错误增量） | `rejected / out_of_order` |
| 计数器回绕 | 旧值 ≥ 量程 95% 且 0 ≤ 新值 ≤ 量程 5% | 接受，增量 = (量程 − 旧值) + 新值 | `accepted_new` |
| 疑似重启/复位 | 读数变小但不满足回绕条件 | 拒绝，避免产生负增量或离谱正增量 | `rejected / value_decrease` |

计数器默认量程为 **100 000 kWh**（构造 `MeterService(store, rollover=...)`
可配置，上报与统计使用同一口径）。回绕判定同时要求"旧值贴近顶部"和
"新值贴近底部"，据此把**回绕**与**设备重启归零/预置到任意值**区分开：
例如默认量程下 `99800 → 200` 判为回绕（增量 400），而 `500 → 10`、
`90 → 5` 判为疑似重启复位并拒绝。

## 统计查询语义

`GET /api/devices/{device_id}/usage?start=...&end=...`（闭区间）：

- 只累加**起点与终点都落在窗口内**的相邻增量。跨越窗口起点的增量不计入，
  避免把窗口外的用电摊到窗口内。
- **离线空档不产生用电量**：窗口内没有读数就是 0；空档前后读数相同则该段
  增量为 0，绝不会按时间长短凭空摊派。
- **重复上报不重复计入**：`(device_id, timestamp)` 是数据库主键，重复数据
  在存储层只有一行。
- 同样的输入（库中数据 + 相同窗口）反复查询得到完全一致的结果，结果按
  时间升序返回，并附带每个增量片段的起止时间与数值（`points`）。

## 并发、幂等与重启

- SQLite 表以 `(device_id, ts)` 为联合主键，`INSERT OR IGNORE` 保证同一读数
  并发提交时只有一个请求真正写入；业务层"查重/查最新 + 写入"在同一把
  RLock 内原子完成，结论确定。
- 多台设备在同一时刻并发上报互不影响。
- 数据持久化在 SQLite 文件（WAL 模式）。服务重启后重新打开同一文件：
  已计入数据不丢失；旧读数重新提交仍判为重复，不重复计入；可在原有序列
  上继续上报，统计连续衔接。

## HTTP 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/health` | 健康检查与各设备读数条数概览 |
| POST | `/api/readings` | 上报一条读数 `{device_id, timestamp, value}` |
| GET | `/api/devices` | 设备列表 |
| GET | `/api/devices/{id}/readings` | 某设备按时间升序的全部读数 |
| GET | `/api/devices/{id}/usage?start=&end=` | 时间窗口用电量统计 |

示例：

```bash
curl -s -X POST localhost:8000/api/readings -H 'Content-Type: application/json' \
  -d '{"device_id":"m1","timestamp":"2026-10-07T10:00:00Z","value":100.0}'
curl -s -X POST localhost:8000/api/readings -H 'Content-Type: application/json' \
  -d '{"device_id":"m1","timestamp":"2026-10-07T10:05:00Z","value":108.5}'
curl -s 'localhost:8000/api/devices/m1/usage?start=2026-10-07T10:00:00Z&end=2026-10-07T11:00:00Z'
# {"device_id":"m1", ..., "total_usage":8.5, "reading_count":2, "points":[...]}
```

## 代码结构

```
app/
  models.py    数据模型与状态/原因枚举
  store.py     SQLite 持久化（主键幂等、线程安全、UTC 归一化）
  service.py   上报校验、回绕判定、增量与窗口统计
  api.py       FastAPI 路由
main.py        服务入口
demo.py        端到端模拟脚本
tests/         按业务组织的单测（conftest 打印业务覆盖汇总）
```
